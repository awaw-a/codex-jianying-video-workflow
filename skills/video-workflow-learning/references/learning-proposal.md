# 经验候选与窄范围升级

先读项目实际发生的反馈与证据，再记录候选。采用文件包既有经验记录结构；安装后的持久位置由工作流配置指定，不在各skill私建一套经验库。

一条候选至少说明：项目与版本、问题触发、用户原意、实际证据、根因或未确认假设、已做修正、修正后的证据、适用边界、拟升级位置、用户决定。没有证据的想法标为候选，不写成已验证经验。

## 分类

| 类别 | 记录方式 | 不应做的事 |
|---|---|---|
| 新增或细化需求 | 记录指令与受影响范围 | 把后来的新要求倒算成此前疏漏 |
| 实现缺陷 | 记录可复现触发与最小修复 | 用新特效掩盖错场/错时钟 |
| 创作取舍 | 记录观察、影响和用户选择 | 把主观建议伪装成技术失败 |
| 环境差异 | 记录版本、工具和实际兼容证据 | 推广成所有软件版本的保证 |
| 已证实的通用方法 | 提出可检验、边界明确的改进 | 把单片规格写入所有模板 |

## 提案与验证

优先修正最小决策点。例如把高风险代表镜头导出检查前置，而不是给每种效果加十条规定。先查看现有规则是否已涵盖；有则纠正执行或测试，不再建重复文件。

向用户说明拟改skill/工具/模板/profile中的哪一处、改前改后行为、证据和风险。长期偏好只改唯一profile；流程说明只改其权威skill/引用；当前状态只由主agent更新。授权只覆盖明确的升级，不扩大到安装新服务或改全局设置。

经用户接受后在授权范围实施、运行skill校验和有意义的工具/场景验证，记录候选与已采纳版本关系。验证不能只检查措辞相同；需要证明新规则在代表任务里改变正确行为。未获接受保持候选，不在下一项目偷偷执行为硬约束。

维护经验时保留历史证据和拒绝/延期原因。发现此前结论过强，主动缩小结论范围；未听的音频仍未听，不用补写“验收通过”修饰历史。
